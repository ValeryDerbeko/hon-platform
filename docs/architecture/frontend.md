# Архитектура фронтенда HON-platform

Документ описывает технологический стек, принципы организации кода и ключевые архитектурные решения фронтенд-части HON-platform. Клиентское приложение представляет собой веб-интерфейс социальной сети, который работает с GraphQL API и разделяет серверные данные с мобильным приложением на React Native.

## Стек технологий

| Область | Технология |
| :--- | :--- |
| Фреймворк | Next.js, React |
| Язык | TypeScript |
| UI-кит | shadcn/ui |
| Стилизация | Tailwind CSS |
| Анимации | Animate UI, Aceternity UI, React Bits |
| Локализация | next-intl (русский и английский языки) |
| Глобальное состояние | Zustand |
| Работа с API | GraphQL, Apollo Client |
| Архитектура проекта | Feature-Sliced Design (FSD) |
| Формы | React Hook Form |
| Валидация | Zod |
| Автотесты | Jest |

## Фреймворк: Next.js и React

Фронтенд реализуется на Next.js и React. Оба инструмента выбраны за широкое распространение, большое сообщество и развитую экосистему: для них существует множество готовых библиотек, примеров и решений типовых задач. Это снижает стоимость разработки и поддержки, а также упрощает поиск разработчиков в проект.

Next.js отвечает за маршрутизацию, рендеринг и оптимизацию загрузки приложения, а React используется для построения интерфейса на компонентах.

## Язык: TypeScript

Проект пишется на TypeScript. Строгая типизация позволяет:

- выявлять ошибки на этапе компиляции, а не в рантайме;
- упрощать рефакторинг и развитие кода;
- документировать контракты компонентов, функций и данных через типы;
- улучшать автодополнение и подсказки в редакторе.

TypeScript используется на всех слоях приложения, включая типизацию ответов GraphQL, схем валидации и пропсов компонентов.

## Стилизация

Для стилизации интерфейса используется Tailwind CSS — вместо CSS Modules. Причина выбора: на Tailwind построена вся выбранная экосистема интерфейса, поэтому отдельный инструмент стилизации не нужен.

- shadcn/ui написан утилитарными классами Tailwind: официальная документация требует установить Tailwind для работы кита, а темизация строится на CSS-переменных, подключаемых через `@theme`;
- Animate UI анимирует примитивы, на которых построены компоненты shadcn/ui, и работает с теми же Tailwind-классами;
- Aceternity UI поставляется только в варианте Tailwind;
- React Bits устанавливается через CLI shadcn/ui и ориентирован на Tailwind-вариант компонентов.

Единый инструмент стилизации избавляет команду от двойной конвенции «где утилиты, а где модули», а компоненты сторонних каталогов копируются в проект без переработки. При стилизации соблюдаются правила: цвета задаются семантическими токенами (`bg-primary`, `text-muted-foreground`) для поддержки тёмной темы, условные классы собираются через `cn()`, а динамическая склейка имён классов из переменных не используется — Tailwind генерирует только классы, присутствующие в исходниках целиком.

### shadcn/ui

В качестве готового набора UI-компонентов используется shadcn/ui. Кит предоставляет компоненты, которые копируются в проект и принадлежат ему, поэтому их можно свободно изменять и стилизовать под дизайн платформы без борьбы с ограничениями библиотеки.

Выбор обусловлен распространённостью и популярностью кита, качеством и современным внешним видом компонентов, а также наличием большого числа готовых тем. Компоненты кита размещаются в слое `shared/ui` и используются как единая база для всех фич и страниц.

### Анимации: Animate UI, Aceternity UI, React Bits

Для анимаций используются три набора компонентов:

- **Animate UI** — анимирует примитивы, на которых построены компоненты shadcn/ui. Сами компоненты остаются прежними, меняется только импорт примитива, поэтому Animate UI совместим с выбранным китом, его темами и разными вариантами поставки shadcn/ui;
- **Aceternity UI** — каталог эффектных анимированных компонентов и секций;
- **React Bits** — популярная коллекция анимированных React-компонентов с большим количеством готовых эффектов.

Эти инструменты выбраны, чтобы сделать интерфейс современным, красивым и плавным. Animate UI используется как основной источник анимаций, так как работает в одной экосистеме с shadcn/ui; Aceternity UI и React Bits применяются точечно для отдельных эффектов и наиболее выразительных элементов.

При использовании анимаций соблюдаются ограничения:

- анимируются преимущественно `transform` и `opacity`, чтобы не вызывать дорогих перерасчётов раскладки;
- учитывается настройка `prefers-reduced-motion` — для пользователей, отключивших анимации, эффекты минимизируются;
- анимация не должна мешать чтению контента и работе с формами;
- компоненты сторонних каталогов адаптируются под тему проекта, а не используются «как есть» в исходном виде.

## Организация проекта: Feature-Sliced Design

Структура проекта строится по методологии Feature-Sliced Design (FSD) версии 2.1 — актуальной спецификации. Подход выбран, потому что он широко распространён во фронтенд-сообществе, близок к отраслевому стандарту, понятен новым разработчикам и активно развивается.

По сравнению с собственной (кастомной) архитектурой FSD даёт готовые, продуманные решения, которые не нужно изобретать самостоятельно. По сравнению с модульной архитектурой он подробнее описывает организацию слоёв и содержит больше ограничений, в частности запрет на кросс-импорты. Эти ограничения уменьшают связность модулей и ведут к более чистой архитектуре.

FSD 2.1 следует принципу «pages first»: код по умолчанию размещается в слое `pages`, а в нижние слои выносится только действительно переиспользуемый код. Не все слои обязательны — минимальная валидная структура состоит из `shared`, `pages` и `app`; слои `features` и `entities` добавляются, когда для них появляется реальное применение, а не «на всякий случай».

### Слои

| Слой | Назначение | Примеры |
| :--- | :--- | :--- |
| `app` | Инициализация приложения: провайдеры, глобальные стили, раскладка уровня приложения, настройка локализации и Apollo Client | `providers`, `styles`, `i18n` |
| `pages` | Крупные блоки интерфейса страниц вместе с их логикой: композиция из фич и сущностей | лента, профиль, медиа, музыка, друзья, сообщества, сообщения, уведомления, настройки, авторизация |
| `features` | Действия и сценарии пользователя | авторизация, создание поста, реакция, комментарий, заявка в друзья, загрузка медиа, управление плеером, отправка сообщения, переключение языка |
| `entities` | Бизнес-сущности и их модель | пользователь, пост, медиа, трек, плейлист, сообщество, сообщение, уведомление |
| `shared` | Переиспользуемая инфраструктура без привязки к бизнес-логике | UI-кит, API-клиент, утилиты, конфигурация, переводы, ассеты |

Слой `widgets` в проекте не используется: актуальная версия FSD не рекомендует его. В реальном коде крупные блоки интерфейса почти всегда включают логику пользовательских сценариев — загрузку данных, состояние, обработку событий, — из-за чего граница между `features` и `widgets` размывается. Блоки, которые традиционно размещали бы в `widgets`, распределяются так:

- композиция, специфичная для конкретной страницы, — внутри этой страницы (`pages`);
- переиспользуемое действие пользователя вместе с интерфейсом для его выполнения — в `features`;
- интерфейс без бизнес-контекста — в `shared/ui`;
- раскладка уровня приложения (например, глобальная панель музыкального плеера) — в `app`;
- переиспользуемое отображение бизнес-сущности — в сегменте `ui` соответствующей сущности. Например, карточка поста, которая встречается в ленте, в профиле и на странице сообщества, размещается в `entities/post/ui`.

Каждый слой состоит из слайсов (например, `entities/post`, `features/create-post`), а слайс — из сегментов:

- `ui` — компоненты и стили;
- `model` — состояние, хуки, типы и бизнес-правила;
- `api` — запросы и GraphQL-операции;
- `lib` — вспомогательные функции слайса;
- `config` — конфигурация и константы.

### Правила импортов

- Слой может импортировать только слои, расположенные ниже него. Например, `features` может использовать `entities` и `shared`, но не `pages`.
- Кросс-импорты между слайсами одного слоя запрещены. Взаимодействие идёт через публичный API слайса (`index.ts`).
- Внутри одного слайса импорты между его сегментами разрешены.
- Слой `shared` не импортирует код из других слоёв.
- Слой `app` находится на вершине и может использовать любые слои.
- Импорты выполняются через алиас `@/`, а не через длинные относительные пути.

### Маршрутизация и FSD

Файлы маршрутов Next.js остаются тонкими: они не содержат бизнес-логики и только подключают соответствующую страницу из слоя `pages`. Провайдеры, глобальные стили и конфигурация приложения размещаются в слое `app`. Такой подход сохраняет совместимость с маршрутизацией Next.js и не нарушает границы слоёв FSD.

## Работа с API: GraphQL и Apollo Client

Для взаимодействия с GraphQL-сервером используется Apollo Client. GraphQL выбран за гибкость: клиент запрашивает ровно те данные, которые ему нужны, без изменения серверных эндпоинтов под конкретный клиент. Это особенно важно, так как к одному GraphQL-серверу обращаются и веб-приложение, и мобильное приложение на React Native: каждый клиент формирует собственные выборки под свой интерфейс.

Apollo Client — стандартное решение для работы с GraphQL на клиенте. В проекте он обеспечивает:

- нормализованный кеш и переиспользование данных между компонентами;
- декларативные запросы и мутации через хуки;
- обновление кеша после мутаций, в том числе оптимистичные обновления для реакций и других быстрых действий;
- постраничную загрузку для лент и списков;
- единую обработку ошибок и состояний загрузки.

GraphQL-операции размещаются в сегменте `api` соответствующего слайса. Для сущностей используются фрагменты, чтобы один и тот же набор полей переиспользовался в разных запросах. Настройка клиента и провайдер Apollo находятся в слое `app`.

## Глобальное состояние: Zustand

Для управления глобальным состоянием используется Zustand. Он выбран потому, что:

- поддерживает инструменты отладки, совместимые с Redux DevTools;
- не требует большого количества бойлерплейта, характерного для Redux;
- позволяет писать короткий и легко читаемый код, который просто понимать и поддерживать.

Zustand хранит только клиентское состояние: настройки интерфейса, состояние музыкального плеера, открытые панели, черновики и другие данные, не принадлежащие серверу. Серверные данные остаются в кеше Apollo Client и не дублируются в глобальном сторе.

Сторы размещаются в сегменте `model` того слайса, к которому относится состояние. Компоненты подписываются на нужные части стора через селекторы, чтобы избегать лишних перерисовок.

## Мультиязычность: next-intl

Для локализации используется next-intl — распространённое решение для мультиязычности в Next.js. Приложение поддерживает два языка:

- русский;
- английский.

Переводы хранятся в файлах сообщений и группируются по пространствам имён, соответствующим страницам и фичам. В компонентах не допускаются захардкоженные пользовательские строки: весь текст выводится через функции next-intl. Средствами библиотеки также форматируются даты, числа и относительное время с учётом выбранной локали.

Настройка локализации и выбор языка размещаются в слое `app`, а переключатель языка реализуется как отдельная фича.

## Формы: React Hook Form

Формы в приложении строятся на React Hook Form. Библиотека оптимизирована: она не хранит введённые значения в состоянии React, а держит их непосредственно в HTML-полях ввода. Доступ к значениям компоненты получают через прокси-объекты библиотеки только там, где это необходимо, в том числе при выполнении запроса. Благодаря этому удаётся избежать лишних перерисовок.

Для простых форм, где нет сложной логики, достаточно обычных HTML-элементов и CSS: такой вариант быстрее и требует меньше кода. React Hook Form применяется там, где форма действительно сложная:

- много полей и зависимостей между ними;
- динамические списки полей;
- загрузка и валидация файлов;
- отображение серверных ошибок;
- пошаговые сценарии.

Библиотека также поддерживает работу с неконтролируемыми полями, что дополнительно снижает количество ререндеров при вводе.

## Валидация: Zod

Для валидации данных используется Zod. Преимущества библиотеки:

- тесная интеграция с TypeScript;
- понятное декларативное описание правил;
- встроенные проверки, которые не нужно писать самостоятельно;
- вывод готовых TypeScript-типов из схемы.

Схемы валидации описываются рядом с формами и бизнес-логикой — в сегментах `model` соответствующих слайсов. Типы, выведенные из схемы (`z.infer`), переиспользуются в компонентах и запросах, поэтому правила валидации и типы не расходятся.

Zod подключается к React Hook Form через резолвер: одна и та же схема проверяет значения полей и формирует типизированные данные для отправки. Сообщения об ошибках валидации локализуются средствами next-intl.

## Адаптивная вёрстка

Интерфейс должен корректно выглядеть на всех основных типах устройств:

- настольный компьютер;
- ноутбук;
- планшет;
- смартфон.

Вёрстка строится по принципу mobile-first средствами адаптивных вариантов Tailwind (`sm:`, `md:`, `lg:`): базовые стили описывают мобильный вариант, а последующие брейкпоинты постепенно расширяют раскладку. Используются стандартные контрольные точки Tailwind CSS:

| Брейкпоинт | Минимальная ширина |
| :--- | :--- |
| `sm` | 640 px |
| `md` | 768 px |
| `lg` | 1024 px |
| `xl` | 1280 px |
| `2xl` | 1536 px |

При вёрстке учитываются:

- отсутствие горизонтальной прокрутки на любой ширине экрана;
- удобные для касания размеры интерактивных элементов на мобильных устройствах;
- перестройка многоколоночных раскладок в одноколоночные;
- адаптация медиа: изображения и видео не выходят за границы контейнера и сохраняют пропорции;
- оптимизация загрузки изображений средствами Next.js.

## Тестирование: Jest

Для автотестов как на фронтенде, так и на бэкенде используется Jest. Единый фреймворк упрощает настройку CI и позволяет разработчикам применять один и тот же инструмент во всех частях проекта.

На фронтенде тестами покрываются:

- утилиты, преобразования данных и схемы Zod;
- хуки и логика состояния;
- компоненты и их состояния (загрузка, ошибка, пустые данные);
- сценарии фич и страниц во взаимодействии.

Тесты размещаются рядом с кодом или в каталоге `__tests__` внутри соответствующего слайса. Внешние зависимости изолируются: запросы Apollo Client и функции next-intl подменяются моками, чтобы тесты не зависели от сети и локали.

## Ключевые договорённости

- Весь код пишется на TypeScript; применение `any` без необходимости не допускается.
- Структура проекта следует FSD: импорты направлены только сверху вниз, кросс-импорты между слайсами запрещены, публичный API слайса задаётся через `index.ts`.
- Весь интерфейс стилизуется средствами Tailwind CSS: компоненты shadcn/ui настраиваются через варианты и CSS-переменные, собственные компоненты пишутся утилитарными классами.
- Серверные данные живут в Apollo Client, клиентское глобальное состояние — в Zustand; дублирование запрещено.
- Пользовательские строки выводятся только через next-intl; поддерживаются русский и английский языки.
- Сложные формы строятся на React Hook Form, правила валидации описываются схемами Zod и переиспользуются как источник типов.
- Интерфейс адаптирован под компьютер, ноутбук, планшет и смартфон.
- Автотесты пишутся на Jest.
