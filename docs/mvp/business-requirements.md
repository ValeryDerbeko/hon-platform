# Бизнес-требования к MVP HON-platform

Документ описывает бизнес-требования к минимально жизнеспособному продукту (MVP) HON-platform. В MVP входит базовый функционал, необходимый для запуска и проверки жизнеспособности платформы. Функционал, выходящий за рамки MVP, помечается соответствующим образом и может быть добавлен в последующих версиях продукта.

## Регистрация и авторизация пользователей

### Регистрация по email

В приложении следует предусмотреть возможность регистрации пользователей классическим способом:
- на странице регистрации пользователь вводит свой email и пароль;
- пользователю отправляется на почту ссылка для подтверждения аккаунта;
- после того, как пользователь переходит по ссылке - регистрация считается завершенной, пользователя перенаправляют на платформу;
- пользователь заполняет в профиле данные о себе.

Следует предполагать, что в системе есть возможность авторизации через аккаунт Яндекса. Поэтому нужно учесть, что если почта пользователя принадлежит сервису Яндекса, то необходимо пользователю давать возможность входит в этот же аккаунт не по паролю, а через YandexID. То есть автоматически связывать аккаунты у которых указана почта Яндекса вне зависимости от способа входа. Если пользователь ввёл данные от другой почты, то вход по YandexID в этот же аккаунт будет не возможен.

Владелец сервера должен иметь возможность самостоятельно настроить служебную почту платформы, с которой будут отправляться письма пользователям. Это необходимо для того, чтобы при регистрации по почте пользователю автоматически приходило сообщение для активации аккаунта.

### Регистрация по YandexID

В приложении следует предусмотреть возможность регистрации пользователя с помощью аккаунта Яндекс пользователя:
- пользователь видит сообщение, что он может войти в систему с помощью его Яндекс аккаунта и жмёт на кнопку соответствующую;
- система регистрирует пользователя по его YandexID при этом предполагается, что у пользователя не заполнены логин с паролем в системе;
- почта должна быть автоматически заполнена из данных по YandexID пользователя. Предполагается, что почта у аккаунта будет заполнена автоматически, но пароль у аккаунта не будет задан
- пользователь заполняет в профиле данные о себе.

В настройках профиля в приложении должна быть возможность установки пароля для аккаунта. Это необходимо для того, чтобы пользователь мог установить пароль для входа при помощи логина и пароля, так как следует предполагать, что почта от YandexID может использоваться для входа в качестве логина. 

Также этот же функционал будет использоваться для смены пароля в аккаунте. 

### Авторизация по логину и паролю

Классический вход в аккаунт через логин с паролем.

### Авторизация по YandexID

Если пользователь входит через YandexID, которая уже зарегистрирована в системе, то вместо процесса регистрации запускается авторизация. 

### Авторизация по QR коду

Необходимо предоставить возможность входа в аккаунт путём сканирования QR кода. Если пользователь авторизован в мобильном приложении платформы, то он может использовать функционал сканирования QR кода, который показывается на странице авторизации в браузере. После сканирования он должен дать подтверждение на авторизацию в его аккаунте. 

### Функционал сброса пароля

Следует предусмотреть возможность установки нового пароля на случай, если пользователь забыл свой пароль.

Порядок сброса пароля:
- пользователь на странице авторизации указывает свою почту;
- рядом с полем ввода пароля должна быть кнопка сброса пароля;
- после нажатия на кнопку сброса пароля пользователю на почту, которая была заполнена в форме отправляется ссылка для его сброса;
- после того, как пользователь переходит по ссылке - его перенаправляет на страницу сброса пароля;
- пользователь вводит новый пароль и повторяет его;
- после этого его перенаправляет на главную страницу приложения, пароль теперь измененный.

## Лента социальной сети

При входе в HON-platform пользователь попадает на страницу с лентой. Она представляет собой способ просмотра постов. 

### Принцип формирования ленты

Лента будет формироваться на основе двух механизмов:
- подписок пользователя: посты других пользователей и сообществ, на которых подписан человек;
- рекомендательная система постов других сообществ / пользователей.

Формирование ленты на основе подписок будет представлено простым способом - отображение постов в хронологическом порядке в зависимости от их публикаций. Посты из подписок будут перемешаны с постами из рекомендаций в виде единой ленты.

Так как HON-platform - это небольшой инди-проект, то может быть недостаточно ресурсов для построения продвинутой рекомендательной системы, поэтому она будет упрощенной. Для каждого пользователя будет составлен перечень сообществ и других пользователей, которых он встречал в ленте. Для каждого из них будет заполняться рейтинг заинтересованности пользователя.

### Рейтинг заинтересованности пользователя

Изначально для всех сообществ и других пользователей будет задан единый рейтинг заинтересованности, который может расти или снижаться от исходного значения. Его значение будет влиять на то, как часто посты данного сообщества будут показываться в рекомендациях. Так как рейтинг для всех сообществ и пользователей единый, то изначально рекомендации будут браться случайным образом.

Будут несколько механизмов, влияющих на изменение рейтинга заинтересованности:

#### 1. Вычисление времени удержания пользователя при просмотре поста 

Для каждой публикации вычисляется время удержания пользователя, что позволяет судить, дочитал ли он пост до конца или пролистал. Для этого рассчитывается среднее время удержания пользователей на конкретном посте, после чего время данного пользователя сравнивается с этой средней величиной. Факт пропуска или задержки влияет на рост или снижение рейтинга.

#### 2. Выставление позитивной реакции на пост

Если пользователь оставил у поста позитивный эмодзи, то это влияет на рейтинг заинтересованности и повышает его для данной подписки у пользователя. 

При этом аналогичный механизм для негативных реакций и комментариев делать не нужно. Негативные реакции могут оценивать контент внутри поста, например, могут отображать реакцию пользователя на новостное событие. Комментарии могут быть как негативными, так и позитивными. Поэтому как для комментариев, так и для негативных реакций нельзя однозначно говорить о том должен ли рейтинг заинтересованности вырасти или понизиться. Но для такого случая продолжает работать оценка рейтинга на основе удержания пользователя на публикации.

#### 3. Явная реакция пользователя через меню действий

У поста будет расположена кнопка для открытия меню действий. Нажатие на неё будет открывать всплывающее меню со списком. Часть из действий будет влиять на рейтинг заинтересованности пользователя по отношению к пользователю или сообществу, опубликовавшему пост.

Действия, влияющие на рейтинг заинтересованности:
- Скрыть посты этого сообщества / пользователя - обнуляет рейтинг заинтересованности пользователя для данного сообщества / пользователя и выставляет блокировку на отображение его публикаций в ленте. Посещение страницы данного сообщества / пользователя будет снимать блокировку, но рейтинг начнет расти заново (автоматически прошлое значение рейтинга не возвращается);
- Показывать меньше постов этого сообщества / пользователя - снижает рейтинг заинтересованности пользователя для данного сообщества / пользователя на определенное значение.
- Отписка от сообщества / пользователя - посты по подписке появляются в ленте не на основе рекомендательной системы, а в хронологическом порядке. При этом отписка должна обнулять рейтинг в начальное значения вне зависимости от того какое значение рейтинга было до этого.

#### 4. На основе интересов других пользователей

Для работы данного механизма необходимо чтобы рейтинг заинтересованности определялся для подписок пользователя тоже. Хотя изначально и предполагалось, что рейтинг заинтересованности будет выставляться только сообществам / пользователям, на которых пользователь не подписан.

Цель данного механизма - повысить рейтинг заинтересованности пользователя для тех сообществ / пользователей, которых пользователь сам ещё не встречал в ленте. Это необходимо для того, чтобы избежать большого числа случайных рекомендаций в ленте, а вместо них показывать посты, которые могут быть интересны пользователю.

Описание данного способа:
- Взять топ наиболее интересных для пользователя сообществ / пользователей, которые больше всего нравятся пользователю просматривать. Например, отсортировать сообщества по рейтингу заинтересованности пользователя и взять 10 с наиболее высоким рейтингом;
- Для каждого из таких сообществ / пользователей определить множество пользователей у которых высоких их рейтинг заинтересованности по отношению к данному сообществу / пользователю;
- По определенным множествам пользователей найти пересечение. Это позволит найти выборку пользователей со схожими интересам, которые смотрят сообщества / пользователей, которые смотрит и пользователь для которого определяли выборку;
- Для каждого пользователя из выборки определяем наиболее интересные для них сообщества / пользователей, которые они смотрят;
- Из полученного множество сообществ / пользователей оставляем только тех, которые не знакомы пользователю;
- Для найденных сообществ / пользователей повышаем рейтинг заинтересованности на определенное значение. Он не должен стать слишком большим. Значение должно быть таким, чтобы не перебить текущие интересные пользователю посты, но если такие кончаются - предоставить данную выборку вместо случайных сообществ / пользователей.

Такой подход повышает вероятность рекомендации интересного поста пользователю при показе нового сообщества / пользователя по сравнению с простой случайной рекомендацией.

Минусы подхода:
- запрос может быть ресурсоемким;
- при малой аудитории запрос может исчерпать свои рекомендации и быть бесполезным;
- механика может поместить пользователя в информационный пузырь;
- рекомендации могут быть не совсем интересны пользователю, так как люди разносторонние и не обязательно пользователям должны нравиться одни и те же сообщества.

### Параметры механизма рейтинговой системы

При реализации рейтинговой системы следует учесть часть параметров, которые могут быть заданы как фиксированные настройки платформы, либо вычисляться индивидуально для каждого пользователя.

- **начальное значение рейтинга заинтересованности** - значение, которое будет выставляться всем другим пользователям и сообществам при их первом появлении в ленте у данного пользователя;

- **значение падения рейтинга заинтересованности при пропуске поста** - величина на которую вырастет снизится рейтинг заинтересованности для данного сообщества / пользователя при определении того факта, что пользователь не читал пост, а проскролил его мимо;

- **окно времени определения пропуска поста** - промежуток времени удержания пользователя, который система воспринимает как пропуск поста. Он формируется на основе минимального и максимального значение. Если пользователь смотрел на пост меньше минимального значение, то это следует воспринимать как быстрый скол вниз не мотивированный пропуском текущего поста. Если пользователь задержался больше максимального значение, то это следует считать как удержание пользователя на посте. При этом верхняя граница должна быть индивидуальной для разных постов, так как посты могут быть разных форматов (фото / видео / текст). Максимальное значение должно быть константой до определения среднего времени удержания. После его определения должно быть вычислено на его основе;

- **значение роста рейтинга заинтересованности при дочитывании поста** - значение на которое будет увеличен рейтинг заинтересованности для сообщества / пользователя в случае дочитывания поста до конца пользователем;

- **окно времени определения дочитывания поста до конца** - промежуток времени удержания пользователя от минимального до максимального значения, который определяет тот факт, что пользователь дочитал пост до конца. Аналогично он изначально формируется из константных значений, а после формирования среднего времени удержания - на основе него;

- **значение роста рейтинга заинтересованности при удержании на посте без дочитывания** - значение на которое вырастет рейтинг, если пользователь удержался на посте дольше чем максимальное время заинтересованности для определения факта пропуска поста, но меньше времени удержания для определения факта дочитывания поста до конца. Значение не должно быть фиксированным, а должно зависеть от значение роста рейтинга заинтересованности при дочитывании поста и времени удержания. Например, таким способом можно определить, что пользователь прочитал половину поста и увеличить рейтинг на половину значения от рейтинга дочитывания;

- **значение роста рейтинга при выставлении положительной реакции** - значение на которое вырастет рейтинг, если пользователь поставил положительную реакцию на посте;

- **значение снижения рейтинга при нажатии на кнопку "показывать меньше постов"** - значение на которое снизится рейтинг, если пользователь явно нажал на действие уменьшение показов постов этого сообщества / пользователя. Нужно определить должно ли значение быть фиксированным или рейтинг должен снижаться на коэффициент.

Некоторые параметры не учтены здесь. Например, при реализации следует определить будет ли рейтинг расти линейно или логарифмически. К примеру, если рейтинг будет расти линейно, то снижение рейтинга при пропуске поста будет слишком мало влиять на рейтинг сообщества / пользователя. Если человеку разонравилось сообщество, он начал пропускать его посты, то нужно будет слишком долго ждать пока пропадут рекомендации этого сообщества / пользователя.

Также следует учесть что при работе ленты нужно найти баланс среди подписок, рекомендаций, постов от случайных сообществ / пользователей.

## Профиль пользователя

Профиль пользователя - это страница, на которой пользователи редактируют и просматривают информацию о себе. На этой странице пользователь может увидеть, как его профиль выглядит для других пользователей. Через неё он может посмотреть на контент, который выкладывал у себя в профиле. А также управлять этим контентом.

### Информация о пользователе

В верхней части профиля в виде шапки отображается информация о том, что это за человек, и краткие сведения о нём, например:
- имя и фамилия;
- дата рождения;
- возможно, другие общедоступные данные (состав следует уточнить при реализации);
- аватарка.

Кроме того, следует предусмотреть возможность установки пользовательской шапки профиля. Шапка представляет собой баннер в виде картинки, которую пользователь может выбрать по своему вкусу. Аватарка при этом размещается поверх данной шапки рядом с данными о пользователе.

### Разделы профиля

Разделы профиля представляют собой части интерфейса, которые внутри себя хранят часть контента, опубликованного пользователем. Например, раздел с фотографиями хранит недавние фотографии, опубликованные пользователем. Кроме того, нажав на кнопку, можно перейти к странице всех фотографий и посмотреть все фотографии, опубликованные пользователем.

Аналогичный функционал должен быть предусмотрен для разделов с видео и музыкой.

Также где-либо на странице профиля должна быть размещена кнопка редактирования профиля. Она не обязательно должна располагаться рядом с разделами - допускается её размещение в другом месте страницы.

### Лента постов пользователя

Профиль можно скроллить вниз - данная часть страницы будет реализована как бесконечный скролл, в котором отображаются посты, опубликованные пользователем. Посты располагаются в хронологическом порядке: от последнего опубликованного и далее вниз.

Посты должны быть представлены в стандартном формате - таком же, какой пользователь может видеть в ленте.

Пользователь может редактировать и удалять свои опубликованные посты, размещённые на его странице.

### Функционал публикации поста

В профиле пользователя будет кнопка для публикации нового поста, где он может заполнить информацией и опубликовать новый пост. Нажимая на эту кнопку, он переходит в интерфейс редактирования (создания) нового поста.

При создании нового поста отображается простой редактор текста. С его помощью пользователь заполняет текст для поста. Он позволяет, например, создавать ссылки, делать текст жирным и выполнять другое структурирование текста.

Фотографии, видео и музыка добавляются отдельно, как вложения к посту. Вложения добавляются отдельным механизмом. Например, при добавлении фотографий они объединяются в карусель, которая встраивается внутрь поста: когда пользователь просматривает пост, он может видеть эту карусель (либо другой просмотрщик фотографий вместо карусели). Аналогичный механизм просмотра должен быть и для видео, музыки.

При создании поста пользователь может ограничить возможность взаимодействия с ним: отключить оставление реакций на пост либо отключить оставление комментариев.

При создании поста должна быть предусмотрена настройка, позволяющая добавить выбранные вложения в соответствующие разделы на странице пользователя. Например, прикреплённые фотографии - в раздел фото, видео - в раздел видео, музыку - в раздел музыки пользователя. Настройка выполняется на том же экране добавления поста, где прикрепляются вложения.

### Опубликованный пост

Каждый пост может состоять из различных опциональных составляющих деталей:

1. функционал просмотра прикреплённых фотографий. Он может быть представлен либо в виде карусели, либо в виде просмотрщика;

2. видеопроигрыватель, встроенный в пост. Когда человек смотрит пост, он может воспроизвести прикреплённое видео и по желанию развернуть его на весь экран специальной кнопкой, встроенной в видеопроигрыватель, либо посмотреть видео в уменьшенном формате внутри поста. При этом следует учесть, что видео может быть опубликовано в вертикальном или в горизонтальном формате, и пост должен адаптироваться под данные размеры;

3. возможность прослушивания прикреплённой к посту музыки. Например, она может быть расположена внизу всего содержимого поста;

4. само содержимое поста, представляющее собой текст с форматированием.

Другие пользователи могут оставлять реакции на посту. Реакции будут представлены не бесконечным и не огромным набором вариантов, а ограниченным списком. Каждая реакция представляет собой эмодзи, который может быть добавлен к посту. Принцип работы примерно такой же, как в Телеграме, но с меньшим количеством возможных реакций. Будут присутствовать как положительные, так и нейтральные, и негативные эмодзи, однако только положительные реакции будут влиять на рейтинг заинтересованности.

Реакции будут отображаться на посту. Рядом с эмодзи будет располагаться счётчик, показывающий количество оставленных реакций определённого типа на данном посту от различных людей. Один человек может оставить только одну реакцию одного типа на посте.

Также у поста будет возможность оставления комментариев. Комментарии могут оставлять как человек, опубликовавший пост, так и другие пользователи, увидевшие этот пост. Комментарии сделаны в упрощённом варианте: пользователи просто оставляют комментарии, и они видны под постом, отсортированные в хронологическом порядке; у каждого комментария есть время публикации. Допускается формирование ответов на комментарии других пользователей. При этом возможность ставить реакции-эмодзи на комментарии других людей не будет добавлена в MVP, чтобы не усложнять продукт на первоначальной стадии разработки. Возможно, в будущих версиях данный функционал будет добавлен.

## Фото и видео пользователя

### Общее описание

Раздел с медиафайлами на странице пользователя предназначен для просмотра фотографий и видео, которые пользователь опубликовал на своей странице. Это не вложения постов, а именно самостоятельные публикации фотографий и видео на странице. Опубликованные пользователем фото и видео будут отображаться в ленте других пользователей, подписанных на него, - не в виде постов, а в виде опубликованных фотографий и видео.

Фотографии и видео отображаются в разделе вперемешку - в виде единой ленты медиафайлов.

Медиафайлы хранятся на сервере и доступны по ссылке. Один и тот же файл может быть добавлен у различных пользователей и сообществ: у каждого из них он отображается в разделе, как будто хранится именно у него, хотя фактически на сервере хранится единственный экземпляр файла.

### Добавление фото и видео

В приложении должна быть функция добавления фотографий и видео на страницу. За одно добавление может быть загружена одна или несколько фотографий и/или видео.

При добавлении медиафайлов пользователю должно быть отображено сообщение, что они будут добавлены в раздел фото и видео на его странице и появятся у других пользователей в ленте.

Медиафайлы могут быть добавлены на страницу независимо либо в альбом.

### Альбомы

У пользователя может быть несколько различных альбомов. Пользователь может создавать, удалять и редактировать их самостоятельно. Альбом представляет собой своего рода папку, которая группирует медиафайлы. В одном альбоме могут находиться как фотографии, так и видео.

У альбома могут быть различные права доступа:
- открытый - альбом доступен для просмотра всем;
- только для друзей - альбом доступен для просмотра только друзьям пользователя;
- закрытый - альбом доступен только для личного просмотра.

У альбома есть настройки: название и права доступа.

### Интерфейс раздела с фото и видео

При переходе в раздел с фото и видео интерфейс должен учитывать как просмотр медиафайлов, не относящихся к альбомам, так и просмотр всех альбомов пользователя с возможностью зайти внутрь альбома.

Следует предусмотреть возможность фильтрации медиафайлов по типу: например, фотографии, длинные видео, короткие видео.

### Просмотр фото и видео других пользователей

Пользователь может заходить на страницы других пользователей, открывать раздел с их фото и видео и просматривать их. Интерфейс раздела аналогичен тому, как отображаются медиафайлы на собственной странице пользователя, но с учётом прав доступа:
- не отображаются медиафайлы и альбомы, доступ к которым закрыт для данного пользователя;
- редактирование медиафайлов и альбомов недоступно.

При этом пользователь может оставлять комментарии и ставить реакции к фото и видео других пользователей.

### Управление фото и видео

Фотографии и видео можно добавлять, удалять и переносить в альбом.

На фото и видео можно ставить реакции и оставлять комментарии - по аналогии с тем, как это работает у постов. Реакции представлены набором эмодзи.

## Музыка пользователя

### Общее описание

Раздел с музыкой на странице пользователя предназначен для прослушивания музыкальных треков, которые пользователь добавил в систему. Цель раздела - создать музыкальный плеер внутри социальной сети: пользователь может зайти в раздел, включить музыку и прослушивать её, не покидая платформу.

### Добавление музыки

Музыка загружается в раздел в формате MP3. Допускается поддержка и других аудиоформатов, однако обязательным требованием является поддержка формата MP3.

У каждого трека должна быть информация о нём:
- исполнитель;
- название трека;
- обложка.

Музыкальные файлы, как и другие файлы платформы, хранятся на сервере и доступны по ссылке. Один и тот же трек может быть добавлен у различных пользователей и сообществ: у каждого из них он отображается в разделе, как будто хранится именно у него, хотя фактически на сервере хранится единственный экземпляр файла.

### Плейлисты

В разделе с музыкой могут быть плейлисты. Плейлист представляет собой своего рода папку, которая группирует музыкальные треки вместе.

При переходе в раздел с музыкой пользователь видит как треки, не относящиеся к плейлистам, так и плейлисты, внутрь которых он может зайти и просмотреть находящиеся там треки.

### Музыкальный плеер

Когда пользователь включает трек, запускается музыкальный плеер, который по функционалу является подобием стандартного плеера. Плеер предоставляет следующие возможности управления:
- кнопка воспроизведения (плей) и паузы;
- кнопка перехода к следующей композиции;
- кнопка перехода к предыдущей композиции;
- ползунок, позволяющий выбрать позицию воспроизведения внутри трека;
- отображение общего времени трека и времени, которое уже прослушано у текущей композиции.

### Источник воспроизведения

Плеер воспроизводит треки по порядку в рамках текущей папки:
- если пользователь включил музыку из общего раздела, то есть среди треков, не входящих в плейлисты - воспроизведение идёт по порядку среди треков, не относящихся к плейлистам;
- если пользователь зашёл в плейлист и включил там какой-либо трек - воспроизведение идёт по порядку среди треков этого плейлиста.
- также должна быть возможность воспроизведения вообще всех треков. Например, кнопка, нажатие на которую приводит к включению воспроизведения как треков без плйлиста, так и всех плейлистов вместе.

### Порядок воспроизведении

У плеера должно быть два режима воспроизведения, каждый из которых переключается собственным переключателем:

1. Порядок следования треков:
   - по порядку - треки воспроизводятся в порядке их расположения в текущей папке;
   - вперемешку - треки текущей папки воспроизводятся в случайном порядке.

2. Поведение при достижении конца папки:
   - остановиться в конце папки - после последнего трека воспроизведение завершается;
   - по кругу - после последнего трека папки воспроизведение начинается сначала, с первого трека.

## Друзья

### Общее описание

Друзьями в социальной сети считаются два пользователя, которые подписались друг на друга. Друзья видят в своей ленте посты друг друга.

Если один пользователь подписался на другого, а второй на первого не подписывался, то первый считается подписчиком второго: публикации второго пользователя будут появляться в ленте подписчика, но при этом он не будет числиться его другом.

### Отправка заявки в друзья

Пользователь может посетить профиль другого пользователя, посмотреть его посты, фотографии, видео, музыку и отправить ему заявку в друзья. После того, как пользователь отправляет заявку в друзья другому пользователю, он становится подписчиком этого пользователя.

### Обработка заявки

Пользователю, которому отправлена заявка в друзья, приходит уведомление о том, что его хотят добавить в друзья. После этого он может принять решение: добавить человека в друзья или отклонить заявку.

- Если пользователь принимает заявку, то оба пользователя становятся друг другу друзьями.
- Если пользователь отклоняет заявку, то отправитель заявки становится подписчиком отклонившего - но только в том случае, если у отклонившего открыта страница. Публикации этого пользователя будут появляться в ленте подписчика, однако он не будет числиться его другом.
- Если страница закрыта, то отправитель заявки не становится ни подписчиком, ни другом: между пользователями не возникает никаких отношений, как и было до отправки заявки.

### Раздел друзей

При просмотре раздела друзей должны быть предусмотрены отдельные вкладки:

1. Друзья - пользователи, которые согласились на добавление в друзья. Это взаимные подписки: текущий пользователь и эти пользователи являются друзьями друг у друга.

2. Подписки - люди, на которых подписался текущий пользователь. Вкладка нужна, в том числе, чтобы была возможность отписаться от этих людей.

3. Отправленные заявки - люди, которым текущий пользователь отправил заявку в друзья, но которые ещё не отреагировали на неё. После реагирования они могут либо подтвердить заявку, либо отклонить её. При подтверждении пользователи становятся друзьями, при отклонении текущий пользователь остаётся подписчиком этого человека при условии, что у того открыта страница; если страница закрыта, он не становится ни подписчиком, ни другом.

4. Входящие заявки - заявки в друзья от других людей, на которые текущий пользователь может отреагировать: либо согласиться и добавить человека в друзья, либо отказаться. Логика обработки заявок описана выше, в разделе "Обработка заявки".

## Сообщества

### Общее описание

Сообщество - это страница в социальной сети, которая представляет группу людей, объединённых по интересам, компанию или другой источник для публикации постов. Примерами сообществ могут служить: тематическое сообщество по интересам, официальный аккаунт компании, новостной канал, блог авторского коллектива.

По сути сообщество - это способ нескольких людей или организации вести одну страницу от её имени и публиковать на ней контент для подписчиков. Содержимое сообщества примерно такое же, как у обычного пользователя: оно может публиковать посты, фотографии, видео и музыку.

Пользователь может вступить в сообщество. Вступление считается подпиской на сообщество - по аналогии с подпиской на других людей. Посты сообществ, в которые вступил пользователь, будут появляться у него в ленте.

При этом есть важное отличие от отношений между пользователями: сообщество не может стать другом пользователю, то есть взаимных подписок между сообществом и пользователем быть не может. Сообщество не может подписываться ни на другие сообщества, ни на других пользователей. Подписываться на сообщество разрешено только пользователям.

### Открытые и закрытые сообщества

Сообщество может быть открытым или закрытым.

Если сообщество открытое, то при подписке пользователь сразу же становится его подписчиком и может просматривать посты, опубликованные сообществом. При этом посты открытого сообщества можно просматривать и до подписки, просто зайдя в его профиль. Подписка означает, что посты сообщества будут дополнительно добавляться в ленту пользователя.

Если сообщество закрытое, то вступление в него происходит по заявке:
- пользователь подаёт заявку на вступление;
- администратор сообщества должен одобрить заявку;
- после одобрения пользователь вступает в сообщество и становится его подписчиком, теперь он может видеть посты сообщества, и они появляются у него в ленте.

До одобрения заявки пользователь, даже зайдя в профиль закрытого сообщества, не сможет увидеть его посты или файлы - фотографии, видео, музыку. Ему доступна только аватарка и название сообщества.

### Роли в сообществе

В сообществе есть две роли: администратор и модератор.

Пользователь, который создал сообщество, автоматически становится его администратором. Администратор обладает следующими правами:
- публикация постов;
- управление файлами сообщества - фотографиями, видео, музыкой;
- подтверждение заявок на вступление в закрытое сообщество;
- назначение модераторов.

Модераторы - это люди, которые обладают теми же правами, что и администратор, но не имеют права назначать других модераторов.

### Управление сообществом

Администратор может:
- удалить сообщество;
- редактировать его;
- передать права владения другому пользователю.

При передаче прав владения новый пользователь становится администратором сообщества, а предыдущий владелец становится модератором.

От прав модератора можно отказаться. Это касается как человека, передавшего владение сообществом другому пользователю, так и обычных модераторов. Отказавшийся от роли модератора становится обычным подписчиком сообщества.
